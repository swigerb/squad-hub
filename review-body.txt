## Security review — PR #88 (H-1, issue #84): APPROVE

Reviewed as the blocking security gate. Verified by execution against the PR head (`56d1be3`), not by reading the diff alone.

### Coverage of every response path — verified
Every byte the hub writes to an HTTP client leaves through exactly two writers in `src/service/hub-service.js`, and both now carry the headers:

- `send()` (line 211) — HTML pages, static assets, API 200s, both 404 shapes, the 403 device-token refusal, the sign-in error page, and `OPTIONS` 204.
- the sign-in `writeHead(302, ...)` (line 230).

`git grep` for `res.writeHead|res.end` on the PR head returns those two sites and nothing else. There is no third response path to miss.

Probed live against a running hub (`serveWeb: true`, OAuth configured). Actual observed statuses and headers:

```
/                   200  XFO=DENY  XCTO=nosniff   (HTML)
/app.js             200  XFO=DENY  XCTO=nosniff   (static)
/api/auth-methods   200  XFO=DENY  XCTO=nosniff   (anonymous API)
/api/me             200  XFO=DENY  XCTO=nosniff   (authenticated API)
/no-such-page       404  XFO=DENY  XCTO=nosniff   (HTML-shaped 404)
/api/nothing-here   404  XFO=DENY  XCTO=nosniff   (API-shaped 404)
/auth/github/login  302  XFO=DENY  XCTO=nosniff   (redirect)
/healthz            200  XFO=DENY  XCTO=nosniff   (not claimed in the PR body; covered anyway)
```

The two API cases are genuinely distinct responses — 200 and 404, not the same refusal twice.

### Precedence — cannot be weakened from within a handler
`...SECURITY_HEADERS` is spread **last** at both writers, so a later key wins over any caller-supplied one. The only two `send()` call sites that pass headers at all pass a literal `Content-Type` (`_static`, `_notFound`/`_signinComplete`/`_signinError`); no header name or value at either writer is derived from request input, so there is no case-variant (`x-frame-options` vs `X-Frame-Options`) duplicate-emission path an attacker can reach. The precedence is a real property here, not just a comment.

### Assertions fail when the control is mutated away — verified
Ran the mutation myself rather than trusting the pasted output:

```
node test/mutate.js --only "security response headers"
  baseline green
  CAUGHT  the security response headers are never sent
          -> "the two security headers land on every response, whatever the path or status" failed, as it must
  1/1 mutations caught
  source restored, baseline re-run: green
```

Mutating the `SECURITY_HEADERS` constant rather than one call site is the right choice: it removes the control from `send()` and the 302 simultaneously, so neither site can be silently uncovered by the other's coverage. The redirect assertion checks `status === 302` before the headers, so the case cannot pass vacuously against a hub that never redirects.

### Existing controls not weakened — verified
The source change is additive: two keys appended to two header objects. Caller override of `Content-Type` and `Cache-Control` is unchanged, the path-traversal normalisation in `_static` is untouched, and the `principal.kind !== KIND_USER` API refusal is untouched. Full suite on the PR head: **1204 passed, 0 failed (153s)** — matching the count the report now claims.

### Docs
`docs/security-report.md` registers both headers in the existing table register, states where they are applied and their precedence, and updates 1,203 → 1,204 (verified accurate). No open-work language, no unshipped-control disclosure, no attacker guidance. H-2 (CSP) and H-3 (Referrer-Policy/HSTS) are correctly absent from the report rather than named as gaps.

### Scope
Targets `dev`, based on the current `dev` tip (`2f966b4`), references #84 in body and commit. Four files, all H-1. No CSP, Referrer-Policy or HSTS work leaked forward.

### Non-blocking observations (pre-existing, not in this diff — do not fix here)
- The WebSocket upgrade rejection writes a raw `HTTP/1.1 401 Unauthorized` to the socket without these headers. Not a framing or sniffing surface (a browser never renders it), so not a defect in H-1 — noted only so it is not mistaken for coverage later.
- `_http` has no outer catch, so a throw outside a handler produces no response rather than a header-bearing 500. Availability, not a header gap.

**Verdict: APPROVE.** No blocking findings.
